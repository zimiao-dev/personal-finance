# Personal Finance V2 需求文档

## 1. 版本定位

本阶段称为 V2，计划发布版本为 `v0.2.0`。

V2 在保留 V1 命令行界面（CLI）的基础上新增 Web API，使相同的个人账单管理能力可以通过 HTTP 访问。

### 1.1 V1 已实现基线

当前 V1 已实现：

- 使用 Python 3.12 和 SQLite 的本地 CLI
- 添加、查看、修改和删除交易
- 按分类、日期范围或组合条件查询交易
- 全部收支统计和日期范围收支统计
- CLI 输入规范化、校验和错误提示
- `main.py`、Model、Service、Repository 和数据库访问分层
- Validator、Model、Repository、Service 和 CLI 自动化测试
- 130 项测试全部通过的回归基线
- 由 uv、`.python-version`、`pyproject.toml` 和 `uv.lock` 管理的可复现环境

V1 当前不包含 FastAPI、Pydantic、SQLAlchemy、Web API、Web 前端或生产部署能力。

### 1.2 V2 计划实现能力

V2 计划新增：

- 基于 FastAPI 的 REST API
- 基于 Pydantic 的 HTTP 请求与响应模型
- 健康检查、交易管理、条件查询和收支统计 API
- API 自动化测试
- API 使用说明和契约设计文档

### 1.3 数据与兼容性定位

- V2 继续使用 SQLite 作为当前数据库
- V1 CLI 必须继续可运行
- API 与 CLI 复用现有 Service 层业务能力
- API 不直接调用 CLI 函数，也不依赖终端输入或输出
- V2 不建立第二套独立的交易业务流程

## 2. V2 核心目标

1. 使用 FastAPI 提供清晰、可测试的 REST API 入口。
2. 使用 Pydantic 定义 HTTP 边界的请求解析、字段校验和响应序列化。
3. 复用并按需演进现有 Service 层，使 CLI 与 API 共享业务调用能力。
4. 保持现有 CLI 功能和使用方式可用。
5. 为 API 成功路径、空结果、未找到、非法输入和依赖异常增加自动化测试。
6. V2 继续使用现有 sqlite3 Repository，并为后续数据访问层迁移保持清晰的 Service 与 Repository 边界。
7. 使用 uv 管理新增依赖并同步更新锁文件。

## 3. 用户角色与使用方式

### 3.1 CLI 用户

本地个人财务管理用户继续通过现有菜单使用 V1 功能。

### 3.2 API 调用方

API 调用方通过 HTTP 请求管理同一套本地交易数据。V2 不引入登录、身份认证或多用户身份概念，因此 API 仍属于本地单用户应用边界。

## 4. API 功能需求

本节定义 API 的业务能力和可验证行为。详细路径、HTTP 方法、请求体、响应体、字段命名和状态码将在后续 `docs/api-design.md` 中设计。

### 4.1 健康检查

用户故事：

作为 API 调用方，我希望检查应用是否能够响应，以确认 Web API 已启动并可访问。

验收标准：

- API 提供无需业务输入的健康检查能力
- 正常运行时返回明确、稳定的健康状态
- 健康检查不创建、修改或删除交易数据
- 健康检查具有独立的自动化测试
- 健康检查用于确认 FastAPI 应用能够响应，不要求访问数据库或验证数据库状态

### 4.2 新增交易

用户故事：

作为 API 调用方，我希望新增一条收入或支出交易，以保存个人财务记录。

验收标准：

- API 接收符合交易创建 Schema 的 HTTP 请求
- Pydantic 在 HTTP 边界校验交易输入
- 合法输入通过 Service 层写入当前数据库
- 成功结果能够明确标识新建交易
- 非法输入返回明确、稳定的 HTTP 错误响应
- API 层不复制 Repository 的 SQL 或持久化逻辑

### 4.3 获取全部交易

用户故事：

作为 API 调用方，我希望获取全部交易，以查看已有财务记录。

验收标准：

- API 通过 Service 层获取交易列表
- 返回结果与当前交易模型的业务字段一致
- 交易按现有公开行为以 ID 降序返回
- 空数据库返回明确且结构稳定的空结果
- API 层不自行重新实现排序或数据库查询

### 4.4 按 ID 获取交易

用户故事：

作为 API 调用方，我希望通过交易 ID 获取单条记录，以查看指定交易。

验收标准：

- API 校验 ID 的 HTTP 输入形式和取值范围
- 合法 ID 原样传递到 Service 层
- 记录存在时返回对应交易
- 记录不存在时返回明确、稳定的未找到响应
- 不存在的记录不会触发写操作

### 4.5 修改交易

用户故事：

作为 API 调用方，我希望修改指定交易，以修正已有财务记录。

验收标准：

- API 接收符合交易更新 Schema 的请求
- Pydantic 校验 ID 和可更新业务字段
- API 通过 Service 层执行更新
- 更新成功后能够返回明确的成功结果
- 目标不存在或未更新任何记录时返回明确、稳定的失败响应
- 更新不会改变目标交易的 ID
- API 层不直接执行 SQL

### 4.6 删除交易

用户故事：

作为 API 调用方，我希望删除指定交易，以移除错误或不再需要的记录。

验收标准：

- API 校验交易 ID
- API 通过 Service 层执行删除
- 删除成功时返回明确的成功结果
- 目标不存在或未删除任何记录时返回明确、稳定的未找到或失败响应
- 删除其他 ID 时不会影响无关交易
- API 层不直接执行 SQL

### 4.7 条件查询交易

用户故事：

作为 API 调用方，我希望按分类、日期范围或两者组合查询交易，以快速定位记录。

验收标准：

- API 支持仅分类、仅日期范围以及分类与日期范围组合条件
- 分类条件使用规范化后的值进行精确匹配
- 开始日期和结束日期必须同时提供
- 日期范围包含开始日期和结束日期
- 开始日期不能晚于结束日期
- 组合查询要求分类和日期条件同时满足
- 查询结果按 ID 降序返回
- 无匹配记录时返回明确且结构稳定的空结果
- API 通过 Service 层查询，不在路由中复制筛选逻辑

### 4.8 获取收支统计

用户故事：

作为 API 调用方，我希望获取全部或指定日期范围内的收支统计，以了解总体财务情况。

验收标准：

- API 支持全部统计和日期范围统计
- 日期范围参数必须成对提供
- 日期范围包含开始日期和结束日期
- 开始日期不能晚于结束日期
- API 通过统计 Service 获取结果
- 返回结果与 `TransactionStatistics` 的业务语义一致
- 没有匹配交易时返回稳定的零值统计结果
- 收支差额由收入减去支出计算，不作为数据库字段持久化

## 5. 输入校验与错误处理

### 5.1 API 输入校验

- API 的 HTTP 请求解析、类型转换和字段校验由 Pydantic Schema 负责
- API 校验规则应覆盖交易金额、交易类型、分类、ID、日期和日期范围等公开输入
- API 不调用 `input()`，也不直接调用 `main.py` 中的 CLI 处理函数
- API 错误响应应具有明确、稳定的结构和可理解的信息
- 具体错误响应格式和 HTTP 状态码在 `docs/api-design.md` 中定义

### 5.2 CLI 输入校验

- CLI 继续使用现有 `validators.py` 进行输入规范化和校验
- V2 不因引入 Pydantic 而移除或绕过现有 CLI Validator
- CLI 现有 `ValueError` 展示和返回主菜单行为应保持兼容

### 5.3 共享业务规则

- CLI 与 API 应复用 Service 层和 Repository 层，不复制两套业务调用与持久化流程
- HTTP 表达方式属于 API 边界，终端提示属于 CLI 边界，两者不应进入 Repository
- 跨入口共享的业务行为应由 Service、Model 或适当的共享领域逻辑承载
- 不应为了复用而让 API 直接调用 CLI 函数，或让 CLI 依赖 FastAPI 路由

## 6. 分层与依赖要求

建议的 V2 调用关系：

```text
CLI 输入
  └─> main.py
       ├─> validators.py
       └─> services/
            └─> repositories/
                 └─> database.py
                      └─> SQLite

HTTP 请求
  └─> FastAPI 路由
       ├─> Pydantic Schema
       └─> services/
            └─> repositories/
                 └─> database.py
                      └─> SQLite
```

各层职责：

- CLI 层：菜单、终端输入、确认、输出和 CLI 异常展示
- API 层：HTTP 路由、请求接收、响应生成和 HTTP 错误映射
- Pydantic Schema：HTTP 请求与响应的数据契约
- Model 层：入口无关的交易和统计业务数据
- Service 层：协调共享业务用例，不依赖 CLI 或 HTTP 展示
- Repository 层：数据访问、条件查询、聚合和数据库行映射
- 数据库层：数据库路径、连接和初始化

V2 继续复用现有 sqlite3 Repository。SQLAlchemy 迁移计划放在后续版本中实施，不属于 v0.2.0 的发布条件。

## 7. 兼容性与回归要求

- V1 主菜单和全部 CLI 功能不能因 API 开发而失效
- 原有 130 项测试应继续通过
- API 与 CLI 应复用业务层，不维护两套独立业务流程
- API 输入校验由 Pydantic 负责，CLI 输入校验继续由 `validators.py` 负责
- API 不要求也不应直接调用 CLI 函数
- 数据库测试必须使用隔离数据库，不得修改真实 `data/finance.db`
- 后续数据访问层迁移不得改变已经确认的交易查询、日期边界、排序和统计语义
- V2 的新依赖必须通过 uv 管理，并提交一致的 `pyproject.toml` 与 `uv.lock` 更新

## 8. 自动化测试要求

API 测试至少应覆盖：

- 健康检查成功响应
- 各交易 API 的主要成功路径
- 空列表、未找到和影响零行等分支
- Pydantic 输入校验失败
- 分类、日期范围和组合查询
- 日期边界和日期参数成对要求
- 全部统计、日期范围统计和零值统计
- Service 调用过程中的业务异常和未预期内部异常到 HTTP 响应的映射

测试隔离要求：

- API 测试不得依赖或修改真实 `data/finance.db`
- Repository 集成测试继续使用临时 SQLite 数据库
- API 路由单元测试可替换 Service 依赖，避免意外访问真实数据库
- 需要数据库的 API 集成测试应使用独立、可重复创建的测试数据库
- 测试不应依赖执行顺序或固定的自增 ID 起始值
- V2 完成前必须运行原有测试和新增 API 测试的完整测试集

## 9. 非功能需求

### 9.1 可维护性

- CLI、API、Schema、Service、Repository 和数据库层职责清晰
- 避免在路由函数中堆积 SQL 或跨层业务逻辑
- 公开数据模型和错误语义应保持一致、可测试

### 9.2 依赖与环境

- V2 新增的 FastAPI、Pydantic 和 API 测试工具通过 uv 管理
- 修改依赖时同步更新 `pyproject.toml` 和 `uv.lock`
- 常规开发和验收使用锁定依赖环境

### 9.3 错误响应

- 非法输入、未找到和内部依赖失败应转换为明确、稳定的 HTTP 响应
- 错误响应不得泄露不必要的数据库或 Python 内部实现细节
- 具体响应结构和状态码在 API 契约设计阶段确定

### 9.4 文档与发布验收

- README 最终补充 API 环境同步、启动和测试方式
- 新增 `docs/api-design.md` 记录稳定后的 API 契约
- 内部文档不得把计划功能描述为已经实现
- `v0.2.0` 完成前执行完整测试、覆盖率检查和干净克隆验收
- 发布前确认 CLI 与 API 均可按照文档启动

## 10. V2 暂不实现的内容

以下内容不属于 `v0.2.0` 范围：

- SQLAlchemy ORM 迁移
- 登录与身份认证
- 多用户及数据隔离
- 权限管理
- Web 前端或 GUI
- 云数据库和云同步
- 预算管理
- 复杂财务分析
- 数据导入导出
- 异步数据库访问
- 微服务拆分
- 生产环境部署承诺

上述能力只能作为未来可能考虑的方向，不得在 V2 文档或发布说明中描述为现有功能。

## 11. 建议实施阶段

### 阶段一：API 需求与契约设计

- 确认 V2 范围、资源语义和错误分类
- 编写 `docs/api-design.md`
- 设计路径、请求体、响应体和状态码
- 在契约评审通过前不提前固化 Repository 实现

### 阶段二：FastAPI 应用骨架和健康检查

- 添加 FastAPI 应用入口
- 实现健康检查
- 建立基础 API 测试方式
- 确认启动应用不会破坏现有 CLI

### 阶段三：Pydantic Schema

- 定义交易创建、更新、查询和响应 Schema
- 定义统计响应和稳定错误响应
- 增加 Schema 校验测试
- 保持 Schema 与内部 Model 的职责边界

### 阶段四：交易与统计 API

- 实现交易新增、获取、修改、删除和条件查询 API
- 实现全部统计和日期范围统计 API
- 通过 Service 层复用现有能力
- 完成未找到、空结果和异常映射

### 阶段五：API 自动化测试

- 完成路由和契约测试
- 完成必要的 API 数据库集成测试
- 验证真实数据库隔离
- 运行原有 130 项测试，确认 CLI 回归基线不受影响

### 阶段六：文档、回归测试和发布验收

- 更新 README 和相关内部文档
- 运行完整测试和覆盖率检查
- 从干净克隆验证环境同步、数据库初始化、CLI、API 和测试流程
- 核对版本号、License、Tag 和 Release Notes
- 完成 `v0.2.0` 发布验收

## 12. V2 完成标准

满足以下条件后，V2 才可进入 `v0.2.0` 发布准备：

- 本文范围内的 API 能力已实现并通过契约测试
- API 路径、请求、响应和错误状态已记录在 `docs/api-design.md`
- V1 CLI 功能保持可用
- 原有 130 项测试与新增 API 测试全部通过
- API 和数据库测试未修改真实 `data/finance.db`
- uv 锁文件与项目依赖一致
- README 包含经过验证的 API 启动和测试步骤
- 完整测试、覆盖率检查和干净克隆验收通过
- 暂不实现的能力没有被写成当前功能
- 项目仍明确定位为本地单用户应用，而非生产级财务系统
